# puffer-cli 245: AgentEnv workflow binding and local runtime integration

`puffer-cli` now treats connection workflow bindings and local workflow runtime
startup as AgentEnv-compatible runtime boundaries instead of Puffer-native
workflow execution.

## Binding Create

`workflow_binding_create` accepts the legacy `pattern` plus
`file_append_path`/`path` shortcut and the generic binding shape used by
workflow UI clients. Generic requests may send `action`, `filter`,
`ignore_filters`, `contact_ids`, `classify_prompt`, and `classify_model`.

Run-workflow callers may also send top-level `workflow_id`, `workflowId`,
`workflow_slug`, or `workflowSlug`. The daemon converts that shorthand into the
persisted compatibility shape:

```json
{"action":{"type":"run_workflow","slug":"<workflow-runtime-id>"}}
```

The persisted JSON field remains `slug`, but the value is the AgentEnv runtime
workflow id used as `:workflow_id` in:

```text
POST /v1/workflows/:workflow_id/execute
```

If both `action` and `file_append_path` are present, `action` wins. If no
generic action or workflow id is present, the daemon preserves the old shortcut
by requiring `file_append_path` and generating a text `file_append` action.
Requests with no action, workflow id, or file append path fail with a clear
contract error.

All binding creation routes persist through the same upsert, subscriber setup,
connection-consumer refresh, and rollback sequence. Paused bindings persist but
skip subscriber startup. If setup fails, a replaced binding is restored or a new
dirty binding is deleted, then connection consumer state is refreshed again.

## Binding Snapshot

Workflow binding snapshots now expose the full serialized action as `action`
next to the legacy summary fields:

- `action_type`
- `action_path`
- `action_format`
- `filter_pattern`
- `model`

Older clients can continue reading the summary fields. New clients should read
`action` when they need action-specific values that have no legacy field.

## AgentEnv Execute Payload

Connection-triggered `run_workflow` actions call the configured runtime with a
single connection input object:

```json
{
  "input": {
    "type": "connection",
    "envelope_id": "...",
    "connection_id": "...",
    "receivedAt": "...",
    "topic": "...",
    "kind": "...",
    "dedup_key": "...",
    "text": "...",
    "payload": {}
  }
}
```

`workflow_binding_json` remains only a Puffer configuration/list snapshot. It
must not be sent as the AgentEnv workflow execute payload.

## Local Runtime

Local workflow mode starts a Puffer-managed AgentEnv Docker Compose stack. It
does not implement a native Puffer workflow executor, reinterpret connectors as
workflow nodes, or reuse an existing local AgentEnv installation.

Puffer writes `<user_config_dir>/workflow-runtime/docker-compose.yml` and runs:

```text
docker compose -f <compose_file> -p puffer-workflow-runtime ...
```

The generated stack has exactly five services:

- `postgres`, using `postgres:14-alpine`
- `redis`, using `redis:7-alpine`
- `migrate`, using the AgentEnv API image with `node dist/database/migrate.js`
- `seed`, using the Postgres image with `psql -f /bootstrap/seed.sql`
- `api`, using the AgentEnv API image and binding
  `127.0.0.1:<local-port>:3000`

For local mode, Puffer generates or preserves:

- `workflow_backend.workspace_id`
- local user id
- local API key
- `API_KEY_PEPPER`
- JWT boot secrets required by the AgentEnv image
- a loopback API port

Only `mode = local`, `api_base_url`, `workspace_id`, and
`api_token_secret_id` are saved in Puffer config. The plaintext API key is
stored only in the Puffer secret vault and is not written to config, Compose,
`.env`, or `seed.sql`.

`ensure_ready` bootstraps config and runtime files, starts Postgres and Redis,
runs migration and seed one-shots, starts the API service, waits for
`GET /v1/health/ready`, and verifies
`GET /v1/workflows/node-definitions` with `X-API-Key` and `X-Workspace-ID`.
Migration, seed, or node-definition failures are surfaced as local runtime
failures instead of falling back to another executor.

`daemon_workflow_runtime::workflow_runtime_client` ensures the local runtime is
ready before constructing a client when `workflow_backend.mode = local`. Cloud
mode keeps the existing HTTP-only path and never touches Docker.
