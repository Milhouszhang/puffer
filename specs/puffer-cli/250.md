# Durable Automation Approval And Runtime Activation

## Run Store

`AutomationRunStore` is the sole durable source of Automation execution state.
Run history is a projection of this store, and the separate Automation
suspension file is removed.

Persisted states are `running`, `awaiting_approval`, `resume_pending`,
`completed`, `rejected`, and `failed`. `awaiting_approval` stores a typed action
intent and an optional continuation checkpoint. `resume_pending` stores the
sent action ID, receipt, checkpoint, attempt count, and last recovery error.

Non-terminal runs retain a normalized definition snapshot, Automation revision,
and spec hash. Resume uses this snapshot. Terminal runs retain revision/hash and
result metadata but discard the large snapshot and checkpoint. All active runs
and at most 500 terminal runs are retained.

The store uses a canonical path-level mutex, re-reads under the lock, performs
version-checked transitions, and atomically replaces the file through a unique
temporary path. Active records must not be lost to history pruning.

## Outbound Actions

Outbound origin is a tagged enum for Session, Monitor, or Automation. Automation
origin contains Automation ID, run ID, step ID, and spec hash. Origin and
routing fields never enter connector input.

Automation reaches a gate by first storing `awaiting_approval`, including a
stable action intent, and then calling idempotent `ensure_draft`. A missing draft
can therefore be recreated after restart. A draft with the same ID but different
content or origin is a corruption error.

Approval policy is either `exact` or `editable_text { input_field }`. The
execute RPC accepts only optional `approved_text`; arbitrary approved input is
not accepted. Exact actions reject edits, and editable text is written only to
the daemon-selected field.

## Delivery And Settlement

Execute, reject, and cancel for one action share a per-action coordination lock.
Different actions may execute concurrently. Store mutexes are never held over a
connector, provider, Docker, or AgentEnv call.

Successful connector delivery is persisted as `sent` before origin settlement.
An Automation run then moves from `awaiting_approval` to `resume_pending` and is
continued under a per-run lock. Delivery remains successful if continuation
settlement fails. The response reports delivery and run settlement separately.

Same-request replay of an already-sent action must not call the connector again,
but it must retry Automation settlement. Definitive pre-dispatch failures become
`failed`; ambiguous delivery becomes `uncertain` and requires duplicate-risk
acknowledgement before another send attempt.

Cancellation is committed before an Automation run is marked rejected. A
settlement failure after cancellation remains recoverable. The first terminal
action state wins an approve/reject race.

Startup recovery scans only non-terminal runs. It materializes missing drafts,
settles sent or cancelled actions, resumes `resume_pending` runs, and fails
closed on origin/content mismatches. There is no polling worker or general
durable queue; normal execution, daemon startup, and explicit retry invoke the
same idempotent reconciliation path.

An action left in `sending` by a previous daemon process becomes `uncertain` at
startup. Recovery never infers delivery success or failure. Replacement store
schemas are explicitly versioned; an unknown version fails with an actionable
reset error and is not silently mutated or deleted.

## Activation And Runtime Capabilities

Activation performs pure compilation, ownership/capability preflight, inactive
AgentEnv artifact deployment, disabled Puffer binding deployment, binding
enablement, and only then marks the Automation enabled.

The runtime state records compiled revision, spec hash, backend identity, and a
capability fingerprint. A changed backend identity makes the deployment stale.
Live event handling performs cheap local identity/hash checks rather than a
remote health request per event.

The catalog publishes only capabilities that the selected runtime can execute.
The current UI surface excludes schedule and webhook triggers. A local runtime
without an executor sandbox does not publish `transform_js`, and activation of
such a plan fails with `automation_runtime_capability_missing`.

## Local Runtime And Deletion

`DaemonState` owns one `LocalRuntimeManager`. Start, ensure-ready, test, repair,
stop, and inspect are serialized by its lifecycle mutex. Helpers return an
updated config instead of silently persisting it. RPC handlers save the config
and call `state.replace_config` before success; a save failure leaves memory
unchanged.

The local runtime directory is mode `0700`. Secret-bearing environment, seed,
and stored config files use atomic non-symlink-following writes with mode
`0600`. Secrets and file contents are excluded from diagnostics.

Automation deletion fails while any run is running, awaiting approval, or
resume pending. With no active run, live bindings are removed before the record.
Deletion does not implicitly cancel or reject runs.

The canonical mutation RPCs are `outbound_action_execute` and
`outbound_action_cancel`. Compatibility aliases, arbitrary `approved_input`,
and the superseded run/suspension schemas are not supported.
