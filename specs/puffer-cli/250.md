# Durable Terminal Automation Approval

This update supersedes `249.md` where it persists continuation suspensions,
uses Automation-specific execute/reject mutations, trusts node review flags, or
advertises schedule, webhook, or local transform capabilities that are not
executable end to end.

## Run Store

`DaemonState` owns one `AutomationRunStore`, which is the sole durable source of
Automation lifecycle state. The separate suspension file is removed and run
history is a sanitized projection of this store.

Run IDs are UUIDs. States are `running`, `awaiting_approval`, `completed`,
`rejected`, and `failed`. `awaiting_approval` stores one opaque action ID, step
ID, immutable action intent, and base-intent hash. There is no continuation
checkpoint, normalized spec snapshot, `resume_pending`, or per-run execution
lock.

A run is stored as `running` before the first runtime call. Startup changes an
interrupted `running` run to `failed` with `automation_run_interrupted`; it does
not replay the run.

The store persists a candidate snapshot before publishing it in memory, uses an
explicit schema version and file mode `0600`, retains all active plus 500
terminal runs, and fails loudly on an unknown schema. History never exposes
action intent. Terminal result JSON is sanitized and capped at 64 KiB;
summaries/errors are capped at 4 KiB.

## Policy And Draft Materialization

Save/compile resolves connector permission through the installed connector
catalog and `outbound_gate::effective_action_permission`. Node-level review
flags may tighten but never weaken review. The Automation-level review setting
does not gate read-only actions and cannot ungate mandatory review. Unknown
permissions and mandatory-review or unknown Agent/`puffer_agent` tools fail
closed; no new idempotency taxonomy is required.

Mandatory-review connector actions must be terminal and top-level. Execution
generates an opaque UUID action ID, persists it with the typed intent in
`awaiting_approval`, then calls idempotent `ensure_draft(action_id, intent)`.
A conflicting existing action is quarantined and the run fails recovery.

Outbound origin is a tagged Session, Monitor, or Automation enum. Automation
origin contains Automation ID, run ID, and step ID. Provenance, routing, trigger
context, and action metadata never enter connector input.

Connector action review metadata selects `exact` or ordered editable-text
aliases with `max_bytes` and `allow_empty`; the default is exact. Draft creation
resolves and stores one `editable_text { input_field }` policy. Conflicting
aliases fail closed. The execute RPC accepts optional `approved_text`, never
arbitrary approved input. All other fields, including destination, are pinned.
The daemon validates the connection/connector/action relation and forwards only
declared connector input.

## Delivery And Settlement

Execute and cancel share one per-action coordination lock and re-read after
locking. Different actions may execute concurrently. Store mutexes are never
held during connector calls, and action coordination is not held together with
the run-store mutex.

All local validation occurs before `sending`. Once connector invocation begins,
an error is `uncertain` unless a future connector contract proves no dispatch.
An action left `sending` by the previous process becomes `uncertain` at startup.

`begin_send` records the client request ID and approved-content hash. Same-ID
replay is idempotent only for identical approved content; changed content fails.
Retrying `uncertain` requires duplicate-risk acknowledgement.

Successful delivery is persisted as `sent`, the action lock is released, and
only then does the matching run become `completed`. A settlement-write failure
does not change delivery success; the response sets `runSettlementPending`, and
same-request replay/startup local reconciliation completes the run without
resending.

Normal Automation rejection uses `outbound_action_cancel`, requires a non-empty
reason, commits `cancelled`, then settles the run as `rejected`. Expiry settles
the run as failed with `automation_approval_expired`.

Cancelling an uncertain action requires `uncertain_delivery_ack`. It records
that cancellation followed uncertainty and fails the run with
`automation_delivery_uncertain_abandoned` plus
`delivery_may_have_occurred = true`; it is never reported as ordinary rejection.

## Startup Reconciliation

Recovery performs bounded local I/O only and runs before mutation RPCs are
served. It first normalizes all stale outbound `sending` actions to `uncertain`,
then reconciles active Automation runs:

- missing action: recreate from stored intent;
- sent action: complete the run;
- normal cancelled action: reject the run;
- cancelled-from-uncertain action: fail with possible delivery;
- expired action: fail with approval expiry;
- draft-ready, failed, or uncertain action: remain awaiting review;
- origin/content/policy mismatch: move the action to non-sendable `quarantined`
  and fail closed.

There is no background continuation worker or Automation run-retry RPC.

## Activation, Lifecycle, And Deletion

The current live trigger surface is Puffer connector events. Schedule/webhook
triggers and unsupported AgentEnv nodes, including local `transform_js`, are
hidden and rejected at activation. Catalog generation does not start Docker.

Activation performs fresh ownership/runtime-target/capability preflight, prepares
required helpers and paused bindings, enables the binding only after helpers are
ready, and marks the Automation enabled last. It stores a non-secret
runtime-target key, not a capability fingerprint. Failure leaves no enabled
Puffer binding and keeps a visible paused/error record.

`DaemonState` owns one local-runtime lifecycle mutex. Persistent Local config is
saved before `state.replace_config`; transient Local config does not replace a
Cloud selection. A newly created secret is deleted best effort if config save
fails. All lifecycle paths use supplied `ConfigPaths`. The runtime directory is
`0700`; secret-bearing env, seed, and stored config files use atomic
non-symlink-following `0600` writes.

A per-Automation lifecycle lock coordinates save/pause, activation, trigger
admission, and deletion. Deletion disables admission/binding, rechecks active
`running` or `awaiting_approval` runs, and either leaves a visible paused record
or removes bindings before the Automation record. It never implicitly resolves
an action.

## RPC Surface

Review queries remain `automation_pending_action_list` and
`automation_pending_action_get`. Automation mutations use
`outbound_action_execute` and `outbound_action_cancel`.

Automation-only `connector_action_execute`,
`automation_pending_action_reject`, and Desktop compatibility wrappers are
removed. Monitor-required `monitor_action_execute` and
`task_monitor_action_execute` aliases remain unchanged.

The outbound action file is mode `0600`. Generic outbound terminal retention
and audit rotation are deferred repository-wide concerns.
