# Desktop AgentEnv Workflow Editor

## Direction

Desktop workflow runtime behavior is daemon-only. The Tauri `BackendState`
compatibility fallback is not an AgentEnv runtime, does not own workflow backend
token/config state, and must return explicit unavailable errors for workflow
runtime methods instead of synthesizing empty success responses.

The Workflows screen now includes a Puffer-side workflow editor. Puffer edits
the same AgentEnv-compatible workflow JSON that AgentEnv visual and JSON
editors use, then sends that JSON through the Puffer daemon to the configured
AgentEnv runtime. Local mode targets the user's AgentEnv Docker/API URL; cloud
mode targets AgentEnv Cloud. The payload shape is the same in both modes.

Puffer owns the shared graph structure only:

- `definition.nodes[]`
  - `id: string`
  - `type: string`
  - optional `name: string`
  - `config: object`
  - optional `trusted: boolean`
  - optional `position: { x: number, y: number }`
- `definition.edges[]`
  - `source: string`
  - `target: string`
  - optional `conditionScript: string`

Node-specific business config schemas remain owned by AgentEnv node
definitions and runtime validation. Puffer can display and edit opaque node
`config` JSON, but it must not hard-code every AgentEnv node schema.

## Transport

- `DaemonClient.request` accepts `requireWebSocket`.
- When `requireWebSocket` is used with a non-`ws`/`wss` client, the request
  fails before invoking `backend_request`; non-workflow requests can still use
  the compatibility fallback.
- `desktop.ts` routes workflow backend get/save/test, runtime list/open/create/
  update/deploy/undeploy/execute/in-memory execution/execution reads, node
  definitions, binding mutations, connection deletion, and monitor workflow
  operations through the shared daemon-only workflow helper with a 15-second
  workflow RPC timeout.
- Daemon workflow RPCs are dispatched to the workflow backend/runtime handlers;
  the desktop fake daemon mirrors this contract only for tests.

## Settings

- Settings includes workflow backend mode, API URL, console URL, workspace ID,
  token entry, save, and connection-test controls.
- Saved tokens are stored through the daemon secret store and only surface to
  the UI as `hasToken`.
- Backend save/test actions do not require loading the Workflows screen and do
  not call `workflow_list`.

## API Flow

- Create sends `{ name, description?, definition }` through `workflow_create`
  to AgentEnv `POST /v1/workflows`.
- Draft saves send `{ name?, description?, definition? }` through
  `workflow_update` to AgentEnv `PUT /v1/workflows/:id`.
- Test runs send `{ definition, input?, triggerNodeId? }` through
  `workflow_execute_in_memory` to AgentEnv
  `POST /v1/workflows/execute-in-memory`.
- Deployed runs call `workflow_execute`, then read executions through
  `workflow_list_executions` and `workflow_get_execution`.
- Deploy and undeploy call `workflow_deploy` and `workflow_undeploy`.
- `workflow_node_definitions` and `workflow_node_definition` expose AgentEnv
  node metadata for editor node selection and future schema-aware UI.

## Workflow Overview

- `workflow_list` returns a snapshot containing runtime workflow records, recent
  runs, connectors, connections, workflow bindings, monitor tasks, and per-area
  error fields.
- Runtime workflow rows search across id, name, status, deployment state,
  description, source, runtime, and workspace metadata.
- Runtime workflow rows do not show raw runtime timestamps; created/updated
  fields remain in the runtime payload but are omitted from the overview and
  metadata disclosure until a human-friendly presentation is added.
- Selecting a workflow leaves the overview and opens a dedicated editor page
  with that workflow's `definition`, name, description, and runtime metadata.
- Runtime or daemon failures render an explicit unavailable state instead of an
  authoritative empty workflow count.
- Puffer event bindings, connector context, connections, and monitor tasks
  remain visible and actionable alongside runtime workflow records.
- Monitor tasks remain client-side workflow context and the panel is hidden when
  there are no monitor tasks, because it is not part of the AgentEnv workflow
  graph.
- The overview does not embed the visual/JSON editor or a details console; those
  live on the dedicated editor page so the list remains a list.
- The old local pipeline graph, run timeline, and selected-node drawer CSS is
  removed from `workflow.css`; the Workflows screen keeps only the overview,
  editor page, canvas, inspector, metadata, and runtime status styles it uses.

## Create Flow

- The top `Create Workflow` action opens a metadata modal instead of immediately
  calling `workflow_create`.
- The modal requires `name` and accepts optional `description`. Submitting it
  enters the dedicated editor page with a local unsaved draft seeded with a
  manual webhook node.
- The draft editor exposes the same visual and JSON editors as selected runtime
  workflows. `Create workflow` posts the current `{ name, description?,
  definition }` payload through the existing daemon `workflow_create` RPC.
- Selecting an existing runtime workflow exits the unsaved draft state and
  loads that runtime workflow into the editor.

## Editor Behavior

- The editor page exposes workflow name, description, visual editor, and JSON
  editor for either a selected runtime workflow or an unsaved create draft.
- The visual editor can add nodes from AgentEnv node definitions. Node details
  are hidden until a node is selected, matching the AgentEnv editor pattern.
- Adding nodes opens an AgentEnv-style node picker modal rather than an inline
  select. The modal supports search, the Trigger/Transformer/Executor
  categories from AgentEnv node definitions, executor subcategory filters, and
  service rows that expand to function nodes instead of dumping every executor
  action as a top-level card.
- Selecting a node opens an inspector for shared node fields and opaque config
  JSON. Position fields are not exposed in the inspector; node positions are
  edited by dragging nodes on the canvas.
- Visual nodes can be dragged with pointer input. Dragging updates each node's
  `position: { x, y }` in the shared workflow definition, and those coordinates
  are reflected in the JSON editor, in-memory test payloads, save payloads, and
  create payloads.
- Node cards expose output and input ports. Dragging from an output port to
  another node's input port creates a real `edges[]` entry; the selected-node
  inspector lists that node's connections and can remove them.
- The visual editor uses a canvas-first layout. The inspector appears beside the
  canvas only while a node is selected, and the layout collapses to one column
  on narrow screens.
- The JSON editor edits the same `definition` object and requires top-level
  `nodes` and `edges` arrays.
- Blank descriptions are omitted from `workflow_create`; descriptions remain
  optional across create and update flows.
- `Create workflow` posts the unsaved draft payload; it does not call
  `workflow_open_ui`, open the AgentEnv console, depend on browser login state,
  or attach a client-generated workflow id.
- Successful creates are inserted into the runtime list, selected in the
  editor page, and can be saved, deployed, run, or test-run through runtime
  actions.
- `Save draft` updates the selected runtime workflow.
- `Test run` executes the current editor definition in memory and displays the
  returned runtime result.
- After a deployed run starts, the UI schedules delayed execution refreshes so
  fast runtime completions appear without pressing `Executions` again.
- Manual `Executions` clicks reuse the same execution refresh path and open the
  runtime workflow in the editor page.
- `openWorkflowConsole`/`openWorkflowUi` remain daemon-only API helpers for the
  configured runtime UI, but editor create/save paths do not use them.

## Tests

- Unit tests cover the daemon-only request guard, workflow API routing options,
  workflow create/update/in-memory payload shape, and explicit `BackendState`
  workflow fallback failures.
- Playwright tests use `tests/support/fakeDaemon.ts` as an explicit WebSocket
  test double for workflow backend/runtime RPCs.
- Workflow UI tests cover list/search, create modal to dedicated unsaved editor
  page flow, editor JSON create, draggable visual node persistence, visual port
  connection syncing into JSON, selected workflow save, in-memory test run,
  deploy/run/execution refresh, unavailable runtime errors, binding
  toggle/delete, connector context, monitor context, and fake daemon runtime RPC
  records.
- The legacy `workflows-create-flow.spec.ts` coverage for the removed local
  `workflow_save` graph editor is deleted rather than carried as fallback
  coverage.
- Settings UI tests cover workflow backend save/test behavior without loading
  runtime workflow lists.
- The fake daemon does not change production fallback semantics; it exists only
  in tests and exercises the daemon contract.
