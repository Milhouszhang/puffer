# Desktop Workflow UI Cleanup

## Direction

The Workflows screen no longer exposes Puffer's temporary visual workflow graph
editor. Product automation creation is expected to move toward the PR465-style
linear builder, while Puffer continues to store and execute AgentEnv-compatible
workflow definitions underneath.

## UI Contract

- Selecting a runtime workflow opens a read-only detail page with metadata,
  recent executions, related event bindings, and the raw runtime record
  disclosure.
- `Create Automation` starts a local automation draft and does not call
  `workflow_create` until a builder can compile the draft into an AgentEnv
  definition.
- The visible desktop UI does not request AgentEnv node definitions, render a
  canvas, expose node dragging, or expose the shared workflow JSON editor.
- The old `WorkflowDefinitionEditor.svelte` component and unused canvas/node
  picker CSS are removed from the desktop bundle.

## Backend Contract

- `WorkflowDefinition` remains the backend payload shape for runtime create,
  update, in-memory execution, and future automation-builder compilation.
- `workflow_node_definitions` and `workflow_node_definition` remain exported by
  the desktop API and mirrored by the fake daemon for future schema-aware
  builders and RPC compatibility.
- `workflow_update` and `workflow_execute_in_memory` remain backend/runtime RPC
  contracts even though the current Workflows screen no longer calls them.
- Connector-triggered workflow bindings, connector context, and monitor task
  context stay visible on the Workflows screen.

## Compatibility

This reduces conflict with upstream native workflow UI and PR465 automation UI
without replacing the AgentEnv runtime integration. A later linear automation
builder, including a loop syntax if needed, should compile user intent into the
same AgentEnv `definition.nodes[]` and `definition.edges[]` structure before it
persists a runtime workflow, rather than creating an arbitrary default trigger
or reintroducing a user-facing node graph editor.
