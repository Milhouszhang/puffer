# puffer-desktop 789: Automation daemon-backed builder

## Summary

The Desktop Automation screen is daemon-backed. It loads saved Automations,
catalog entries, preview results, and run history through product-level
Automation RPCs instead of mutating local-only UI state or calling workflow
runtime RPCs directly.

## API Contract

For the Automation screen, the Desktop API layer exposes:

- `listAutomations`
- `getAutomation`
- `saveAutomationRecord`
- `deleteAutomationRecord`
- `loadAutomationCatalog`
- `syncAutomationPreview`
- `runAutomationPreview`
- `loadAutomationRunHistory`

These helpers are daemon WebSocket-only. Desktop persists only the supported
`automation_save` fields: `id`, `expectedRevision`, `status`, and `spec`.
Runtime workflow ids and binding slugs are never surfaced or saved by Desktop.

## Builder Mapping

Desktop maps daemon `AutomationRecord` DTOs into the existing card/detail view
model. UI-generated specs preserve source provenance:

- blank builder saves `source: { type: "blank" }`.
- prompt-created builder saves `source: { type: "natural_language", prompt }`.
- template builder saves `source: { type: "template", template_id }`.

Missing UI triggers serialize as manual triggers, scheduled triggers as
AgentEnv node trigger refs, git triggers as Puffer connection trigger refs, and
instructions/tool selections as linear AgentEnv node steps.

Catalog trigger templates are cloned into `AutomationTriggerSpec`. Only
connector fields that currently persist into specs and generated bindings are
shown. Catalog actions are stored as AgentEnv node refs with connector metadata
in config, while human-approval requirements are reflected in the Automation
review policy.

Natural-language creation treats explicit manual/local/no-external-tool
constraints as higher priority than domain keywords such as message or reply.
Those prompts start from the catalog Manual run trigger with no preselected
connector tools. The default Puffer agent execution step remains unchanged.

Automation builder and detail pages include a per-automation `Run location`
selector with Local and AgentEnv Cloud choices. New Automations default from the
saved Automation Runtime mode. Saved specs include `run_location`, and the old
`Cloud Agent Environment` wording is not part of the Automation UI.

If a stored spec contains unsupported richer semantics such as custom filters,
contact ids, loops, or custom AgentEnv config, Desktop only patches
name/description/instructions and preserves the stored source, triggers, flow,
and review policy.

## Runtime Settings

Settings exposes the existing `workflow_backend_*` daemon contract through an
Automation-named pane. The user-facing entry is `Automation Runtime`, not
Workflows. Labels cover runtime mode, API URL, Automation Console URL,
workspace, token, and connection test without using Workflow product language.

Local mode is presented as Puffer-managed runtime state. It does not expose API
URL, workspace, token, or env-var inputs because the daemon generates local
runtime config, credentials, and Docker environment files on demand. AgentEnv
Cloud mode exposes API URL, console URL, workspace, and token fields.

The builder exposes a `Configure Runtime` action that opens Settings directly
to the Automation Runtime pane. The older workflow backend API helpers remain
available for legacy workflow surfaces and daemon internals, but the Automation
product UI no longer routes users through a Workflows-labeled settings entry.

## Test Run Contract

`Test Run` first saves the current detail form, then calls
`automation_sync_preview` for the saved revision, then calls
`automation_run_preview`. Preview sync must not publish live connector bindings
or deploy workflows, and it must preserve an already-current deployed runtime
instead of downgrading it to draft sync. Preview errors are shown in the detail
page. The UI reloads run history after a preview request; sync failures keep
the local error row because the daemon does not write preview history before a
preview request.

Desktop does not execute outward connector actions directly. Approval metadata
is informational in the Automation screen; human-gated execution remains owned
by the monitor approval RPC path.

## Fake Daemon

The Playwright fake daemon implements the Automation RPC store, revision checks,
catalog, explicit preview sync, live compile/deploy, preview preconditions, and
run history so UI tests exercise the real daemon contract. Preview does not
implicitly deploy a stale or not-compiled runtime.

Hard-coded prototype trigger choices remain only as menu fallback when the
daemon catalog is unavailable, preserving the designed trigger entry points.
Tool/action choices come from the daemon catalog only, so Desktop cannot save a
fake static action that the Automation runtime cannot compile or execute.
