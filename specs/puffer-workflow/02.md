# puffer-workflow update 02

`puffer-workflow` is now a narrow AgentEnv-compatible Workflow Runtime HTTP
client. It no longer owns native workflow definitions, validation, cron
scheduling, file-backed run storage, or DAG execution.

## Removed Native Surface

The local implementation modules were removed:

- `schema.rs`
- `store.rs`
- `cron.rs`
- `runner.rs`

Consequently, the crate no longer exports `WorkflowDefinition`,
`WorkflowStore`, `DagRunner`, cron matching/deduplication, native run indexes,
or local trigger schema validation.

## Runtime Client

`WorkflowRuntimeClient` is the only execution entry point. Runtime config
contains an API root URL, API key, workspace id, and timeout; local and cloud
execution differ only by those settings.

The client normalizes `api_base_url` once and appends `/v1/...` per request, so
roots with a trailing `/v1` do not produce `/v1/v1`.

All requests send `X-API-Key`. Workspace-scoped workflow calls additionally
send `X-Workspace-ID`; auth context and node-definition discovery do not.

Supported operations:

- `GET /v1/auth/api-key-context`
- `GET /v1/workflows/node-definitions`
- `GET /v1/workflows`
- `POST /v1/workflows`
- `GET /v1/workflows/:id`
- `POST /v1/workflows/:id/deploy`
- `POST /v1/workflows/:id/execute`
- `GET /v1/workflows/:id/executions`
- `GET /v1/workflows/:id/executions/:executionId`
- `POST /v1/workflows/execute-in-memory`

Auth-domain and workflow-domain response contracts stay endpoint-specific:

- `GET /v1/auth/api-key-context` must return a bare context object.
- Workflow endpoints must return an AgentEnv envelope with top-level `data`.

## Errors And Connection Test

Error classification is stable and UI-facing:

- `401` -> `invalid_token`
- `403` -> `permission_denied`
- `404` -> `workspace_inaccessible`
- transport/connect/timeout failures -> `runtime_unreachable`
- invalid JSON or unexpected response schema -> `incompatible_runtime`
- other non-success HTTP responses -> `service_error`

`test_connection()` returns a structured two-step report:

1. workflow API surface validation via `GET /v1/workflows/node-definitions`
2. workspace access validation via `GET /v1/workflows`

If phase 1 fails, phase 2 is marked `skipped`. Draft, undeployed, or invalid
workflow execution failures are surfaced directly from the configured runtime;
there is no fallback to local DAG execution.
